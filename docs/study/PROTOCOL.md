# Nemosyne flagship study protocol

Status: Draft package.

## Study name
Find the Fraud

## Core hypothesis
For defined analytical tasks involving relationships and multidimensional structure, a spatial and embodied analytical interface can improve human discovery and understanding relative to a conventional 2D analytical interface, without unacceptable costs in precision, workload, comfort, or navigation.

## Conditions
1. 2D control condition
2. Desktop-3D condition using the Nemosyne desktop path
3. VR-3D condition using the WebXR headset path

All conditions share the same task family, task wording, scoring rubric, and dataset version, unless a documented exception is approved before collection begins.

## Primary task
The participant is given a structured transaction dataset and asked to identify anomalous or fraudulent node(s) or relationships. The exact task specification should be represented in the machine-readable task artifact and mirrored in the human-readable task description used in the protocol.

## Participant flow
1. Consent and disclosure
2. Condition assignment using the pre-defined counterbalanced order
3. Brief task framing using the same wording across conditions
4. Trial execution
5. Outcome capture: answer, response time, confidence, workload
6. Debrief or qualitative follow-up as permitted by the ethics plan

## Researcher role during the trial
The researcher role is governed by a fixed protocol state (Passive / Prompt / Assisted), recorded per trial, not assumed constant across the study. Any ad-libbing, intervention, or deviation must be logged in the observer record and reflected in the analysis set if relevant.

## What this protocol does not claim
This protocol does not claim that any single subcomponent of the immersive interface is responsible for any observed effect. The result is about the implemented interface bundle as a whole unless otherwise specified.

## Known limitations
This study should not be used to claim general superiority of all immersive workflows, all spatial layouts, or all embodied interfaces. The claim is limited to the defined task family and the implemented conditions in this package.

## Freeze requirements
The protocol is not frozen until:
- the task definition is fixed
- counterbalancing is determined and recorded
- the consent and data dictionary match the actual data pipeline
- the version file is populated
- the analysis plan is fixed before data collection begins

## Governance note
Any post-freeze change must be documented as a protocol deviation. The study package should not silently change after collection begins.
